# Changing a rule

Scope: this repository, and every product's rule pages. Open when: changing, proposing or merging a rule, here or in a product's rule pages, or a word budget fails.

**One home per rule.** Find the rule's current owner and the pages that lean on it; change it there; delete what it supersedes in the same pull request, never reword it; turn any other copy into a pointer. Git history is the archive. Shorter must never mean weaker: a cut that drops a live requirement is a loss, not a saving. The cold reviewer holds this; the machine holds what follows.

**What the machine holds.** His ruling of 20 October 2026, word for word in [decision 0021](../juku-library/DECISION-0021-RULEBOOK-AUDIT.md), replacing the 8 October size signals: one in, one out, the cut counted by machine rather than declared. `product-reads/rules-check.py` runs in `check.sh` here; a product runs it from a pinned rulebook commit once its own pull request adds the line, and until then nothing checks these there by machine:
- **The word budgets.** The reading path (here `HOW-WE-BUILD.md` and `README.md`; in a product `AGENTS.md` and `design/CONSTITUTION.md`) and all active rule text (here every root page and library page, `juku-library/` and the upgrade log excluded; in a product `AGENTS.md`, `CLAUDE.md`, `NAMES.md`, `design/` and a root `design-system.md`) each have a budget written in the script. Over either fails; the cut that makes room lands in the same pull request, where the count sees it. If two pull requests that each fit merge one after the other and `main` goes over, every open pull request is red until one lands a cut: the next pull request to land owes it, a P1 repair included, cutting in the same change. The complete screen path is reported on every run. A product's requirements, roadmap and locked figures are never cut to fit: they are not budgeted.
- **`Replaces:`.** A pull request that changes a rule page carries one line, `Replaces: <the text or page it supersedes>; products: <product pages updated, or none>`, or `Replaces: nothing — not a check because: <why it cannot be a machine check>`. Read from the pull request as it stands; the reviewer never sees it, and blocks from the diff any superseded text left standing.
- **The constitution's shape.** A product's `design/CONSTITUTION.md` has only the headings *Tokens*, *Units*, *Money*, *Domain law* and *Approved by picture*; every line under the last (or the words "None yet.") carries a date and the path or link of the approved picture or rehearsal; at most 450 words, at most 80 before the first heading.
- **The exam.** The reviewer's brief (this repository's `AGENTS.md`, a product's `## Review guidelines`) ends with short counterexamples; on a change to a rule page the reader answers those the change makes applicable, from the pages as they will stand, and a wrong answer or a contradiction is blocking. A question is added or removed with its rule; the briefs are read from `main`, so a change is judged by the questions already there.

**A ruling of his about how we build is not on the record until it is in this repository.** **Until first revenue**, unrelated audits and shared-platform construction are paused (agreed 13 October 2026, #204 section 5); delivery-blocking defects are still repaired; cleaning the rules themselves is not paused (his ruling, 20 October 2026: *"do it now (this overrides the 'standalone cleanup only from first revenue' line)"*).

**Batches.** Word changes go in small dependency-coherent pull requests, each asked once per round, each conflict it settles listed in it. A rule or design change updates its executable tests where they apply.

**When a change is justified.** His ruling about how we build; or the same material failure in two separate product tasks, or one severe security or data-loss incident, where repairing the product is not enough (`CHARTER.md` §13). Removing a rule, or correcting wording, needs neither.

**"Build" here** takes the open pull request that is ready, highest priority first, oldest within a priority. Each carries `Priority:` set by test: **P1** stop the line (a reproducible failure that blocks a required build, check, review or deploy, lets through what should be refused, loses, duplicates, corrupts or deletes work or data, or crosses a trust boundary wrongly, naming the case); **P2** repair (a reproducible wrong result short of that); **P3** build (approved new capability); **P4** observe (removing it would change nothing that runs). Ready comes first: one waiting on his answer is not ready. One with no `Priority:` line gets one from the first session to read it, written into its body. His asking for something makes it authorised, not P1. With none ready, the top agreed `proposal` issue is next (`library/ideas-for-later.md`); with neither, say so and stop.

**Merging.** By pull request only; `main` is protected and requires `check`, which is green only on a commit the reviewer has read with nothing blocking. The CTO settles and merges without him. The session brings the branch up to date with `main` immediately before asking; after its last fix and its one ask it enables auto-merge (squash); if `main` moves and blocks the merge, it updates and asks for a fresh read. A proven defect's repair, and a change he rules himself, need no proposal. A pull request that changes what runs adds its line to `library/upgrade-log.md`. The private products have no branch protection, so their sessions merge by hand once green; a session that cannot merge hands it to another session, never to him.

**The check's self-test runs in parts**: a pull request runs the core and the parts measured to read a changed file; a change to `check.sh`, `review-gate.py` or a workflow, a push to `main`, a file no part is measured to read, or a red or unfinished `main` runs every part.
