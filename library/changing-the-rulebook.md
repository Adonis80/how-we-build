# Changing a rule

Scope: this repository, and every product's rule pages. Open when: changing, proposing or merging a rule, here or in a product's rule pages.

**One home per rule.** Find the rule's current owner and the pages that lean on it; change it there; delete what it supersedes in the same pull request, never reword it; turn any other copy into a pointer. Git history is the archive. Shorter must never mean weaker: a cut that drops a live requirement is a loss, not a saving. The cold reviewer holds this; the machine holds what follows.

**What the machine holds** (his ruling, 20 October 2026: one in, one out, replacing the 8 October size signals). `rules-check.py` runs in `check.sh` here; a product runs it from a pinned rulebook commit once its own pull request adds the line, and until then the reviewer alone holds these in that product:
- **The word budgets.** The reading path (here `HOW-WE-BUILD.md` and `README.md`; in a product `AGENTS.md` and `design/CONSTITUTION.md`) and all active rule text (here every root page and library page, `juku-library/` excluded; in a product its rule pages) each have a budget written in the script. Over either fails. A change that needs room cuts elsewhere in the same pull request: one in, one out, counted, not declared. The complete screen path is reported on every run. A product's requirements, roadmap and locked figures are never cut to fit: they are not budgeted.
- **`Replaces:`.** A pull request that changes a rule page carries one line, `Replaces: <the text or page it supersedes>; products: <product pages updated, or none>`, or `Replaces: nothing — not a check because: <why it cannot be a machine check>`. Read from the pull request itself; its truth is the reviewer's to judge.
- **The constitution's shape.** A product's `design/CONSTITUTION.md` has only the headings *Tokens*, *Units*, *Money*, *Domain law* and *Approved by picture*; every line under the last carries a date and the path or link of the approved picture.
- **The exam.** The reviewer's brief (this repository's `AGENTS.md`, a product's `## Review guidelines`) ends with short counterexamples; on a change to a rule page the reader answers those the change makes applicable, from the pages as they will stand, and a wrong answer or a contradiction is blocking. The briefs are read from `main`, so a change cannot remove its own question before it is judged; a question goes in the change after its rule's.

**A ruling of his about how we build is not on the record until it is in this repository.** **Until first revenue**, unrelated audits and shared-platform construction are paused; delivery-blocking defects are still repaired; cleaning the rules themselves is not paused (his ruling, 20 October 2026).

**When a change is justified.** His ruling about how we build; or the same material failure in two separate product tasks, or one severe security or data-loss incident, where repairing the product is not enough (`CHARTER.md` §13). Removing a rule, or correcting wording, needs neither.

**"Build" here** takes the open pull request that is ready, highest priority first, oldest within a priority. Each carries `Priority:` set by test: **P1** stop the line (a reproducible failure that blocks a required build, check, review or deploy, lets through what should be refused, loses or corrupts work or data, or crosses a trust boundary wrongly, naming the case); **P2** repair (a reproducible wrong result short of that); **P3** build (approved new capability); **P4** observe (removing it would change nothing that runs). Ready comes first: one waiting on his answer is not ready. With none ready, the top agreed `proposal` issue is next (`library/ideas-for-later.md`); with neither, say so and stop.

**Merging.** By pull request only; `main` is protected and requires `check`, which is green only on a commit the reviewer has read with nothing blocking. The CTO settles and merges without him. After its last fix and its one ask, the session brings the branch up to date with `main` and enables auto-merge (squash); if `main` moves and blocks the merge, it updates and asks for a fresh read. A pull request that changes what runs adds its line to `library/upgrade-log.md`. The private products have no branch protection, so their sessions merge by hand once green; a session that cannot merge hands it to another session, never to him.

**The check's self-test runs in parts**: a pull request runs the core and the parts measured to read a changed file; a change to `check.sh`, `review-gate.py` or a workflow, a push to `main`, or a red `main` runs every part.
