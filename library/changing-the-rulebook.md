# Changing the rulebook

Scope: this repository. Open when: changing a rule, proposing, prioritising or merging a change to this repository, or a word budget fails.

**"Build" here takes the open pull request that is ready, highest priority first and oldest within a priority** (his priority model, 22 September 2026, [decision 0001](https://github.com/Adonis80/how-we-build/issues/57)). This repository has no `roadmap.json`; its queue is its open pull requests, and each carries a `Priority:` line in its body, set by test rather than by feel: **P1**, stop the line — a reproducible failure that blocks a required build, check, review or deploy, lets through what should be refused, loses, duplicates, corrupts or deletes work or data, or crosses a trust boundary wrongly, and it names the failing case; **P2**, repair — a reproducible wrong result short of that; **P3**, build — approved new capability with no failing case; **P4**, observe — removing it would leave what runs unchanged. His asking for something makes it authorised, not P1: priority is the state of the system, not who asked. Ready comes first so priority cannot bulldoze a dependency or a decision that is his — a pull request waiting on his answer is not ready, and the next is taken. One with no `Priority:` line gets one from the first session to read it, written into its body so no later session derives it again. A session started on *build* with this repository chosen reads them in that order and moves one on — answers its findings, pushes the round's fixes as one push, asks once — or closes one that is stale. With none ready, the top agreed `proposal` issue is next, its pull request opened when that work starts ([decision 0020](../juku-library/DECISION-0020-PROPOSALS-QUEUE.md), `library/ideas-for-later.md`, which ranks and debates them); with neither, there is nothing to build here: say so and stop. An improvement reaches a pull request only once its proposal is agreed; a proven defect's repair, and a change he rules himself, need no proposal. **Until first revenue** unrelated audits and shared-platform construction are paused; delivery-blocking defects are still repaired; cleaning the rules is not paused (his ruling of 20 October 2026, decision 0021).

By pull request only; `main` is protected. `check.sh` runs in CI and refuses a file not on the list, anything that looks like a secret, and — in a pull request — a commit the reviewer has not read clean: unread, or read and left a blocking finding on. Word budgets it holds (below). **Its self-test runs in parts** (#187, item 3, [#190](https://github.com/Adonis80/how-we-build/pull/190)): in a pull request, a fast core and only the parts measured to read a changed file, so a page change runs seconds of it where it ran the whole, 18 to 22 minutes; every part on a push to `main`, on a change to `check.sh`, `review-gate.py` or a workflow, on a file no part is measured to read, and while `main`'s own newest finished check is red or none has finished, since a run of parts trusts `main`'s whole run. So a red `main` is repaired by an ordinary pull request, which runs whole, and nothing holds it. Shown live on [#194](https://github.com/Adonis80/how-we-build/pull/194): its page change ran the core alone in 14 s (run 38182594910). Adding a rule, step, file, check or agent needs the charter's gate (§13): the same failure twice, in two separate product tasks. Removing one, or correcting wording, needs no gate; nor does a change the Chairman rules himself. **The CTO settles and merges changes to this page and this repository, without the Chairman** (his ruling, 9 September 2026: "you are the CTO — don't ask me about such things in future"; and again on 22 September, handed a question about how far one of his own rulings reached: *"dont stop to ask me technical decisions, you are CTO"*). He is asked for money, a permission, a product outcome or a picture, and nothing else. The reviewer still reads every change cold, and the gate above still applies. **And the merge is the session's own, here and in every product: step 7 of the loop** (his ruling, 25 September 2026: *"a code session merges its own pull request once its checks are green. I grant that permission once; the merge is never handed to me or to another session."*). So no pull request's next action names him or another session as the hand that merges it. His look at a material user-facing change still comes first (step 6, `CHARTER.md` §12); what changed is only whose hand merges. **Here that hand is GitHub's auto-merge** (his tap, 11 October 2026, on #187: *"auto-merge on"*): after its last fix and its one ask, the session enables auto-merge (squash) on the pull request and ends its turn, waiting on nothing. Bring the branch up to date with main immediately before asking. If main moves again and prevents merging, update and obtain a fresh read (agreed 13 October 2026, #204, section 3; #193 was read clean, then held behind `main` and read again). `main` requires `check`, green only on a commit the reviewer has read clean, so GitHub merges when the read lands and the wake re-runs the check, and never an unread commit: shown on #191, enabled while `check` was red and merged a minute after the clean read (run 38163629022). This repository's alone: the private products have no branch protection on GitHub Free, so their sessions keep merging by hand, as step 7 says.

**If a session truly cannot merge** (his ruling, 25 September 2026, after #98 was merged by hand in a chat session): a session that can merge its own pull request does; one whose own guard refuses, or that has no hands, hands the merge to another session, with the words to start it, and never to him.

**One in, one out, by machine** (his ruling of 20 October 2026, word for word in [decision 0021](../juku-library/DECISION-0021-RULEBOOK-AUDIT.md); it replaces his 8 October size signals). `product-reads/rules-check.py`, run by `check.sh`, holds two hard budgets: the reading path (`HOW-WE-BUILD.md` and `README.md`) and the active rules (every root page and library page, `juku-library/` and the upgrade log excluded). Over either fails, and the cut that makes room must land in the same pull request, where the count sees it; a stated cut that has not landed opens nothing. If two pull requests that each fit merge one after the other and `main` goes over, every open pull request is red until one lands a cut: the next pull request to land owes it, a P1 repair included, cutting in the same change. A pull request that changes a rule page carries `Replaces: <the text or page it supersedes>; products: <product pages updated, or none>`, or `Replaces: nothing — not a check because: <why>`: the check requires the line; the reviewer never sees it, and blocks from the diff any superseded text left standing. Run by a product with `--product` over its rule pages (`AGENTS.md`, `CLAUDE.md`, `NAMES.md`, `design/`), it also holds that product's `design/CONSTITUTION.md` to the headings *Tokens*, *Units*, *Money*, *Domain law* and *Approved by picture*, each approval dated and naming its picture, at most 450 words and at most 80 before the first heading; a product runs it from a pinned rulebook commit once its own pull request adds the line, and until then nothing checks these there by machine.

**What a rule change owes.** For each rule it changes: find the current owner and the consumers it affects, by focused search, not by reading everything; make them agree; delete what the change supersedes; keep every live requirement. Shorter must never mean weaker: a trim that drops a requirement is a loss, not a saving. The cold review holds this (`AGENTS.md`); `check.sh` does not. The cold review also holds **the exam** (decision 0021): the reviewer's brief (this repository's `AGENTS.md`, a product's `## Review guidelines`) ends with short questions; on a change to a rule page the reader answers those the change makes applicable, from the pages as they will stand, and a wrong owner, a contradiction or no answer is blocking. A question is added or removed with its rule; the briefs are read from `main`, so a change is judged by the questions already there.

**Batches.** Word changes go in several small pull requests, each one dependency-coherent and asked once per round (his brief, 9 October 2026: *"A review of a small words change now costs a few cents, so several small batches are cheaper than one big one."*). A page is moved, merged or reworded whenever that removes stale, duplicated or conflicting text, every operative condition kept whole at its owner and each conflict listed in its pull request, inside a change that touches it or as cleanup of its own ([decision 0017](../juku-library/DECISION-0017-SIZE-SIGNALS-AND-RECONCILIATION.md), his goal of 8 October 2026: dead text *"deleted so that the rulebook will always be completely up to date and current"*; [decision 0016](../juku-library/DECISION-0016-LOCALISED-REVIEWS.md) H). Rulings made under the lifted tidying freezes stay quoted in their own pull requests and records. The spend guard that stays is one ask per round, its fixes in one push (`library/reviewer.md`).

**What it does not promise.** A stale line nobody connects to a change can survive until cleanup or a failure finds it.

**A ruling of his about how we build is not on the record until it is in this repository**, exactly as a product decision is not until it is in that product's.

**The upgrade log.** A pull request that changes what runs adds its one line to `library/upgrade-log.md` in the same pull request; the gate is red until the pull request changes that page, and the cold review reads that the change is its line.
