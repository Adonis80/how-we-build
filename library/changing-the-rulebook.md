# Changing the rulebook

Scope: this repository. Open when: changing a rule, proposing, prioritising or merging a change to this repository, or a page reads over its size target.

**"Build" here takes the open pull request that is ready, highest priority first and oldest within a priority** (his priority model, 22 September 2026, [decision 0001](https://github.com/Adonis80/how-we-build/issues/57)). This repository has no `roadmap.json`; its queue is its open pull requests, and each carries a `Priority:` line in its body, set by test rather than by feel: **P1**, stop the line — a reproducible failure that blocks a required build, check, review or deploy, lets through what should be refused, loses, duplicates, corrupts or deletes work or data, or crosses a trust boundary wrongly, and it names the failing case; **P2**, repair — a reproducible wrong result short of that; **P3**, build — approved new capability with no failing case; **P4**, observe — removing it would leave what runs unchanged. His asking for something makes it authorised, not P1: priority is the state of the system, not who asked. Ready comes first so priority cannot bulldoze a dependency or a decision that is his — a pull request waiting on his answer is not ready, and the next is taken. One with no `Priority:` line gets one from the first session to read it, written into its body so no later session derives it again. A session started on *build* with this repository chosen reads them in that order and moves one on — answers its findings, pushes the round's fixes as one push, asks once — or closes one that is stale. With none ready, the top agreed `proposal` issue is next, its pull request opened when that work starts ([decision 0020](../juku-library/DECISION-0020-PROPOSALS-QUEUE.md), `library/ideas-for-later.md`, which ranks and debates them); with neither, there is nothing to build here: say so and stop. An improvement reaches a pull request only once its proposal is agreed; a proven defect's repair, and a change he rules himself, need no proposal. **Until first revenue** (agreed 13 October 2026, [#204](https://github.com/Adonis80/how-we-build/issues/204#issuecomment-6145865695), section 5), standalone cleanup ([#174](https://github.com/Adonis80/how-we-build/issues/174)), unrelated audits and shared-platform construction are paused; delivery-blocking defects are still repaired.

By pull request only; `main` is protected. `check.sh` runs in CI and refuses a file not on the list, anything that looks like a secret, and — in a pull request — a commit the reviewer has not read clean: unread, or read and left a blocking finding on. Sizes it reports and never refuses (below). **Its self-test runs in parts** (#187, item 3, [#190](https://github.com/Adonis80/how-we-build/pull/190)): in a pull request, a fast core and only the parts measured to read a changed file, so a page change runs seconds of it where it ran the whole, 18 to 22 minutes; every part on a push to `main`, on a change to `check.sh`, `review-gate.py` or a workflow, on a file no part is measured to read, and while `main`'s own newest finished check is red or none has finished, since a run of parts trusts `main`'s whole run. So a red `main` is repaired by an ordinary pull request, which runs whole, and nothing holds it. Shown live on this page's own pull request, [#194](https://github.com/Adonis80/how-we-build/pull/194): `selftest: run core, it changes library/changing-the-rulebook.md, read by the core alone`, the step done in 14 s (run 38182594910) where #192's, one page too, took 21 min 53 s (run 38167495715). Adding a rule, step, file, check or agent needs the charter's gate (§13): the same failure twice, in two separate product tasks. Removing one, or correcting wording, needs no gate; nor does a change the Chairman rules himself. **The CTO settles and merges changes to this page and this repository, without the Chairman** (his ruling, 9 September 2026: "you are the CTO — don't ask me about such things in future"; and again on 22 September, handed a question about how far one of his own rulings reached: *"dont stop to ask me technical decisions, you are CTO"*). He is asked for money, a permission, a product outcome or a picture, and nothing else. The reviewer still reads every change cold, and the gate above still applies. **And the merge is the session's own, here and in every product: step 7 of the loop** (his ruling, 25 September 2026: *"a code session merges its own pull request once its checks are green. I grant that permission once; the merge is never handed to me or to another session."*). So no pull request's next action names him or another session as the hand that merges it. His look at a material user-facing change still comes first (step 6, `CHARTER.md` §12); what changed is only whose hand merges. **Here that hand is GitHub's auto-merge** (his tap, 11 October 2026, on #187: *"auto-merge on"*): after its last fix and its one ask, the session enables auto-merge (squash) on the pull request and ends its turn, waiting on nothing. Bring the branch up to date with main immediately before asking. If main moves again and prevents merging, update and obtain a fresh read (agreed 13 October 2026, #204, section 3; #193 was read clean, then held behind `main` and read again). `main` requires `check`, green only on a commit the reviewer has read clean, so GitHub merges when the read lands and the wake re-runs the check, and never an unread commit: shown on #191, enabled at 18:23 with `check` red, still open through the red, merged by GitHub at 19:17, a minute after the clean read (run 38163629022). This repository's alone: the private products have no branch protection on GitHub Free, so their sessions keep merging by hand, as step 7 says.

**If a session truly cannot merge** (his ruling, 25 September 2026, after #98 was merged by hand in a chat session): a session that can merge its own pull request does; one whose own guard refuses, or that has no hands, hands the merge to another session, with the words to start it, and never to him.

**A repair or an upgrade is never refused for length alone, and the dead text leaves in the same change** (his ruling, 8 October 2026, [decision 0017](../juku-library/DECISION-0017-SIZE-SIGNALS-AND-RECONCILIATION.md)). `check.sh` prints sizes against targets: the operating page 600 words, the screen law 450, a library page 4,000 bytes (`library/hypersolid.md` 6,500). A reading over target is a signal, never a failure, and never a cleanup debt on an unrelated change.

**What a rule change owes instead.** For each rule it changes: find the current owner and the consumers it affects, by focused search, not by reading everything; make them agree; delete what the change supersedes; keep every live requirement. Shorter must never mean weaker: a trim that drops a requirement is a loss, not a saving. The cold review holds this (`AGENTS.md`); `check.sh` does not.

**Batches.** Word changes go in several small pull requests, each one dependency-coherent and asked once per round (his brief, 9 October 2026: *"A review of a small words change now costs a few cents, so several small batches are cheaper than one big one."*). The 25 September tidying freeze (no page moves, splits or rewording for tidiness; one session's word changes in one pull request, read once) is replaced whole, by this brief and by two later records of his: his goal of 8 October 2026, [decision 0017](../juku-library/DECISION-0017-SIZE-SIGNALS-AND-RECONCILIATION.md), *"to completely remove all of the bloat and conflicting information so that the result is a super clear, easy to understand and easy to follow rule book"*, with dead text *"deleted so that the rulebook will always be completely up to date and current"*; and [decision 0016](../juku-library/DECISION-0016-LOCALISED-REVIEWS.md) H, agreed under his *"Yes, go ahead."* of 8 October: *"Stale wording is removed in dependency-coherent batches, every operative condition kept whole at its triggered owner, each conflict listed in its pull request."* So a page is moved, merged or reworded whenever that removes stale, duplicated or conflicting text, every live requirement kept: inside a change that touches it, since standalone cleanup waits for first revenue (above). His 5 October words lifting the later October freeze, *"We have to lift that ruling completely and focus on delivering a system with all the wastage cut out"*, point the same way. Rulings made under the freezes stay quoted where they were made: their own pull requests and records. The spend guard that stays is one ask per round, its fixes in one push (`library/reviewer-asking.md`).

**What it does not promise.** A stale line nobody connects to a change can survive until cleanup or a failure finds it.

**A ruling of his about how we build is not on the record until it is in this repository**, exactly as a product decision is not until it is in that product's.
