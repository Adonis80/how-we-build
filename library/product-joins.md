# How a product joins

Scope: every product under this rulebook. Open when: adding a product to the map, or setting up its repository.

1. **The map.** One pull request here adds its line to the README's *Products under this rulebook* and its name to *Where each product's plan lives*, its name to `ROWS` and its repository to `PRODUCTS` in `board/build.py` (and the gate's loosening fixtures in `review-gate.py` that key on the last entry of `PRODUCTS`). That file is part of the gate, so the pull request gets the risky read. Until it merges, the product's slices park at the read. He adds the repository to the Roadmap's read key (`library/roadmap.md`).
2. **The kit.** `python3 product-reads/setup.py NAME --commit <a commit of main> --apply` makes the private repository or takes over the one that exists, and opens a pull request in it with the gate, the wake, `verify`, and a starter `AGENTS.md` and `roadmap.json` where it has none. A differing gate stops it unless `--replace-gate`. It needs one setup token that can create repositories and write workflows, asked of him once, never per product. Without `--apply` it only says what it would do: run it so first, with an old commit of `main` (accepted) and an unmerged pull request's head (refused). It has not run for a real product: no product has joined by it yet. The reviewer App is already on all his repositories.
3. **Its pages and Project**: as `library/carries-sessions.md` lists; the Project set from `library/project-instructions.md`.
4. **Joining → joined.** A product is *joined* once its first real pull request has shown the route: the gate red while unread, `verify` green, one signed read of the exact commit, the wake, the gate green; a second ask bought no second read; a new commit without the ready mark stayed unread. The word changes in a pull request, only then; which products have shown the route is each product's own pull request to say.

**The ready mark, a builder's rule in every product.** After its pre-flight (`library/reviewer.md`), a builder takes the pull request out of draft and pushes the round's last fix with, above it, one commit that changes no file, in one push, and ends its turn. The mark's message carries `Review-Ready: yes` and `Review-Parent: <the full id of the commit beneath it>`, each alone on a line. It never waits on `verify` first: the asker, `ask-product-reads.yml`, every ten minutes, leaves a mark whose `verify` has not passed and asks once it has. A read is asked of that commit only, once; a push after it needs a new mark. By hand, a session with write access here dispatches `review-product.yml`, which refuses a draft, a moved head, a commit that is not the mark, a `verify` not passed on it, and a commit already read or being read. A read that began and never finished is asked again only by a builder who has looked, with `again`; a run that died before it began, by a new mark; a read refused before anything was spent ("budget refused, nothing spent") is asked again without the word. The mark and `verify` are signals, not a boundary: the reviewer's check on the commit it read is what counts.
