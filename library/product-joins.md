# How a product joins

Scope: every product under this rulebook. Open when: adding a product to the map, or setting up its repository.

1. Its repository's `AGENTS.md` begins with one line: `Rulebook: https://github.com/Adonis80/how-we-build — read HOW-WE-BUILD.md before anything else, then What every product carries in its README.` Below that, only what is true for that product, ending with a short `## Review guidelines` section: the pointer to the brief (*The independent reviewer*), the least of it the tool needs in front of it, and the hazards particular to that product.
2. Its Claude Project's instructions are the template (`library/project-template-product.md`), blanks filled.
3. One line in *Products under this rulebook* in the README, one in *Where each product's plan lives*, its name in `ROWS` in `board/build.py`, in the order decision 0007 sets, and its repository in `build-board.yml`'s product list; the gate holds both to the first list, both files are part of the review gate, so this pull request gets the risky read. Until it merges the product is not on the list the reviewer reads, so its slices park at step 5. The board draws four rows and its selftest names them, so a fifth product's row changes those fixtures in the same pull request. Nothing automates this pull request yet.
4. The reviewer needs no install: he set the App's access to all his repositories on 3 October 2026, his word, not checked from a session ([decision 0013](../juku-library/DECISION-0013-AUTOMATIC-PRODUCT-REVIEWER.md)). The product's gate comes from the starter kit: `python3 product-reads/setup.py NAME --commit <a commit of main> --apply` makes the private repository, or takes over the one that exists, and opens a pull request in it with the gate, the wake, `verify` and a starter `AGENTS.md` and `roadmap.json` where it has none. It needs one setup token that can create repositories and write workflows; a session's own token reaches only the repositories it was started with, so he is asked for it once, never per product. Without `--apply` it only says what it would do. It merges nothing and joins nothing on the rulebook's side.
5. **Joining** is a product on the map whose kit is merged and whose first real pull request has not yet shown the route. **Joined** is after that pull request showed: gate red unread, `verify` green, one signed read of the exact commit, the wake, gate green; a second ask bought no second read; a new commit without the ready mark stayed unread. The word changes in a pull request, only then. The setup script, the asker and the checks are built and have not run: no product has joined this way yet.
6. **The ready commit, a builder's rule in every product.** After its own review a builder adds one commit that changes no file. Its message carries `Review-Ready: yes` and `Review-Parent: <the full id of the commit beneath it>`, each alone on a line, and no other commit of the pull request carries either. A read is asked of that commit only, never of work still moving. `review-product.yml` refuses a draft, a head that moved, a commit that is not the mark, a `verify` that has not passed on it, and a commit already read or being read. A push after the mark moves the head off it, so a new mark follows. A read that began and never finished is asked again by nobody but a builder who has looked, with `again`.
