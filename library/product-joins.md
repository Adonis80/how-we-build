# How a product joins

Scope: every product under this rulebook. Open when: adding a product to the map, or setting up its repository.

1. Its repository's `AGENTS.md` begins with one line: `Rulebook: https://github.com/Adonis80/how-we-build — read HOW-WE-BUILD.md before anything else, then What every product carries in its README.` Below that, only what is true for that product, ending with a short `## Review guidelines` section: the pointer to the brief (*The independent reviewer*), the least of it the tool needs in front of it, and the hazards particular to that product.
2. Its Claude Project's instructions are the template (`library/project-template-product.md`), blanks filled.
3. One line in *Products under this rulebook* in the README, one in *Where each product's plan lives*, its name in `ROWS` in `board/build.py`, in the order decision 0007 sets, and its repository and name in that file's `PRODUCTS`; the gate holds both to the first list, the file is part of the review gate, so this pull request gets the risky read. Until it merges the product is not on the list the reviewer reads, so its slices park at step 5. The board draws four rows and its selftest names them, so a fifth product's row changes those fixtures too. The board's read key, `BOARD_READ_TOKEN`, reads only the repositories it was made for, so the Chairman adds the new one to it (`library/build-board.md`); until then its page says it could not be read. Nothing automates this pull request yet.
4. The reviewer needs no install: he set the App's access to all his repositories on 3 October 2026, his word, not checked from a session ([decision 0013](../juku-library/DECISION-0013-AUTOMATIC-PRODUCT-REVIEWER.md)). The product's gate comes from the starter kit: `python3 product-reads/setup.py NAME --commit <a commit of main> --apply` makes the private repository, or takes over the one that exists, and opens a pull request in it with the gate, the wake, `verify` and a starter `AGENTS.md` and `roadmap.json` where it has none. A differing gate of its own stops it before anything is written unless `--replace-gate`; `--display` and `--about` print the join's lines. It needs one setup token that can create repositories and write workflows; a session's own token reaches only the repositories it was started with, so he is asked for it once, never per product. Without `--apply` it only says what it would do; run so the first time, with an old commit of main (accepted) and then an unmerged pull request's head (refused). It merges nothing.
5. **Joining** is a product on the map whose kit is merged and whose first real pull request has not yet shown the route. **Joined** is after that pull request showed: gate red unread, `verify` green, one signed read of the exact commit, the wake, gate green; a second ask bought no second read; a new commit without the ready mark stayed unread. The word changes in a pull request, only then. The asker and the checks have run: the asker looks at every product every ten minutes and has asked reads on Hemz OS and Myst pull requests (run 38103802798, 11 October 2026). The setup script has not run for a real product: no product has joined by it yet, and which products have shown the route above is each product's own pull request to say.
6. **The ready commit, a builder's rule in every product.** After its own review, the pre-flight (`library/reviewer-asking.md`), a builder takes the pull request out of draft, then pushes the round's last fix and, above it, one commit that changes no file, in one push, and ends its turn. The mark's message carries `Review-Ready: yes` and `Review-Parent: <the full id of the commit beneath it>`, each alone on a line. It never waits on `verify` before marking: the asker, `ask-product-reads.yml`, the rulebook's one timer (every ten minutes, his ruling of 4 October 2026), leaves a mark whose `verify` has not passed and looks again on its next tick, asking once it has (run 38103802798, 11 October 2026: Hemz-OS#145 left at 02:05 for the product's own check, asked at 02:15; its next mark likewise at 02:35 and 02:45), so the wait buys nothing, and a mark pushed afterwards runs `verify` a second time on a commit that changes nothing (Hemz-OS#146, 11 October 2026: four hours idle, then two runs). And it never ends a turn promising to act when a check or a read finishes, since nothing wakes it: the slice waits at step 5 of the loop for its read, and the next slice begins. A read is asked of that commit only, never of work still moving, and the asker asks for it once; by hand a session with write access here dispatches `review-product.yml`, which refuses a draft, a head that moved, a commit that is not the mark, a `verify` that has not passed on it, and a commit already read or being read. No product gets a timer, token or schedule. A push after the mark moves the head off it, so a new mark follows: a second round is a fix and a new mark above the old one. A read that began and never finished is asked again by nobody but a builder who has looked, with `again`; a run that died before it began, by a new mark. A read the spending check refused before anything was sent, signed "budget refused, nothing spent", is no read, and is asked again without the word. The mark and `verify` are the product's own, so whoever can push there can write both: signals, not a boundary. The check that matters is the reviewer's, on the commit it read.
