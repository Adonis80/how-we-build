# The deploy, in shape

Scope: every product with a live site. Open when: building or changing a product's deploy.

**The shape.** Deploys run from CI with the deploy key as a repository secret, so no session holds it. CI builds the app, deploys it as a preview and smoke-tests that exact deployment; a merge to `main` promotes the same deployment, never a rebuild, records the previous production deployment first, smokes the live addresses, and if they are red promotes the previous one straight back and fails loudly. The host's own Git integration stays off: it would put every push into production untested.

**Four traps, each of which cost Hemz OS real runs.** The deploy tool reads GitHub-flavoured environment variables and a `github.com` remote as an integration deploy, which a private repository on the free plan refuses with no visible error: hide both from the deploy call. A team-scoped key works where a project-scoped one dies with a misleading missing-project message. Promoting a preview-built deployment mints a production copy, so the check passes on the smoked id or on a deployment whose original is the smoked id. The edge serves the new build a little after the host calls it live: ask again for a couple of minutes before calling it red.

**Previews go to `next.<product>.juku.pro`.** After its smoke, the newest preview takes that name through the host's alias call, moving it off the last, and is smoked as a stranger there before it is handed over, behind the same lock as the live site. The name is a DNS-only CNAME at Cloudflare to the host, added once per product by him; until it exists, a preview is handed over at its own address.

**A build already live is not deployed again** (the free plan allows 100 deployments a day across the whole account). Before its one deployment CI fingerprints what it would ship (the build output without timings, the commit stamp normalised, the target, and the pulled settings without any per-pull token) and ships the fingerprint as a file in the deployment; it compares it, by the file's SHA-1 in the host's file tree, with what production serves (on `main`) or the newest finished previews (on a branch). A match deploys nothing; the reused deployment is smoked as if new. A re-run always deploys, the lever for a change only the host holds; anything not read deploys.

**A preview is deleted once it has served its purpose.** After production is confirmed live, CI deletes the project's finished previews older than two hours, keeping production, the rollback target, what each named address serves, what any of those was copied from, and any preview a still-open pull request could stand on. A keep that cannot be read deletes nothing; the list is printed first; nothing in it turns the run red. The host rate-limits deletes per account, so a pile may take several runs.
