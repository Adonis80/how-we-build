# The deploy, in shape

Scope: every product with a live site. Open when: building or changing a product's deploy.

**The deploy, in shape.** Deploys run from CI with the deploy key held as a repository secret, so no session of any kind ever holds it — and this says what is built, because no product can read another product's repository to find out. CI builds the app, deploys it as a preview and smoke-tests that exact deployment; a merge to `main` promotes the same deployment — never a rebuild, never "whatever is newest" — then smokes the live addresses and, if they are red, promotes the previous production deployment straight back and fails loudly. The previous deployment is recorded before anything moves. The host's own Git integration stays off on purpose: it would put every push into production untested. Four things cost Hemz OS real runs and need cost the next product none: the deploy tool reads GitHub-flavoured environment variables and a `github.com` remote as an integration deploy, which a private repo on the free plan refuses outright with no visible error, so both are put out of its sight for the deploy call; a team-scoped key works where a project-scoped one authenticates and then dies with a misleading missing-project message; promoting a preview-built deployment mints a production copy rather than repointing production, so the check passes on the smoked id **or** on a deployment whose original is the smoked id; and the edge serves the new build a little after the control plane calls it live, so ask again for a couple of minutes before calling it red.

**A preview is deleted once it has served its purpose (his ruling, 17 October 2026: *"previews are deleted once they have served their purpose. And therefore, they cannot pile up."*).** After production is confirmed live, CI deletes the project's finished previews (READY, ERROR, CANCELED or BLOCKED) made over two hours ago, each row held by its own project, state and time rather than the query's word. It keeps production, the rollback target, what each named address serves, what any of those was copied from (the host names it as `meta.originalDeploymentId`; a copy's source, made in the same run, is also kept by time), and any preview a still-open pull request could stand on. A keep that cannot be read deletes nothing; the list is printed before anything goes, and nothing in it turns the run red. On the first run the host answered 429 after 200 deletes, so a pile can take several runs to clear; the host's documentation keeps a deleted deployment recoverable for 30 days (its `deployment.cleanup` event fires only after that period). It gives back none of the host's day. Shown on the Roadmap, [run 39050615164](https://github.com/Adonis80/how-we-build/actions/runs/39050615164): a new copy went live, 477 old previews were listed and 200 deleted, none refused, and every keep stayed. Hemz OS's, which also keeps an open pull request's previews by the commit each carries and the ten newest a branch may reuse, is [Adonis80/Hemz-OS#166](https://github.com/Adonis80/Hemz-OS/pull/166), shown on its merge, [run 39052733987](https://github.com/Adonis80/Hemz-OS/actions/runs/39052733987): production went live, 284 old previews were listed and 19 deleted, none refused, before the host answered 429, and every keep stayed. The Roadmap's own run had deleted 200 a minute before ([run 39055797585](https://github.com/Adonis80/how-we-build/actions/runs/39055797585)), so the host's limit on deletes looks to be the account's, not each project's.

**A build already live is not deployed again (his ask, 15 October 2026: the host's free plan allows 100 deployments a day across every project on the account, and on 13 October it ran out and blocked every product).** After the build and before its one deployment (on `main`, the staged production build that is then promoted, never rebuilt), CI fingerprints what it would ship — the build output without its timings, the commit stamp a build bakes in put back to one word by the build's own rule, the target, and the pulled settings and variables without any token minted per pull — and ships the fingerprint as a file in the deployment, since the host keeps no metadata sent with one. The host's file tree gives that file's id as the SHA-1 of its bytes, so a run compares without downloading: on `main` with what production serves, on a branch with the newest finished previews of any branch, since sessions building at once move a shared preview name off each other. A match deploys nothing; the reused deployment is smoked as if new and on a branch takes the preview name. Holding its worker to the commit it was built from, carried beside the fingerprint, is cited on the pull request a run shows it on, not claimed here. A re-run always deploys, the lever for a change the host alone holds, such as a secret a pull reads as blank; anything not read deploys. Shown on Hemz OS, [Adonis80/Hemz-OS#161](https://github.com/Adonis80/Hemz-OS/pull/161): run 38899774241, 16 October 2026, logged `unchanged:` and made no deployment.

**A preview waiting for his approval is at `next.<product>.juku.pro`, in every product (his ruling, 1 October 2026: *"all previews should be simpley just have the prefix (next.) … that way you can just overwrite old previews with the new ones"*; restated 17 October 2026: *"all previews to be assessed for approval go to next.[insert project name].juku.pro"*).** `<product>` is the name the live site has before `.juku.pro`: `hemz`, `myst`, `roadmap`. After its smoke, the newest preview takes that name through the host's alias call, moving it off the last, and is smoked as a stranger there before it is handed over; it sits behind the same lock as the live site. The Chairman sets the name up once per product, in two places. First, a DNS-only CNAME at Cloudflare to the host, with the same target as the live name's. Second, the name added to the product's own project at the host (Settings → Domains), left on Production. Choosing Preview there asks to link the repository, which is never done, because the host's Git integration stays off (above). Without the project's domain the host refuses the alias ([run 39059448651](https://github.com/Adonis80/how-we-build/actions/runs/39059448651): HTTP 400), and the run warns and hands over the preview's own address. As a Production name, it serves the live site after a production run until the next preview takes it. On 17 October 2026: Hemz OS uses `next.hemz.juku.pro`; the Roadmap's first preview landed at `next.roadmap.juku.pro` that evening ([run 39061103850](https://github.com/Adonis80/how-we-build/actions/runs/39061103850)); Myst's record exists and its deploy does not yet take the name; Phena takes it with its first deploy.
