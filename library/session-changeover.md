# Session changeover

Scope: every session, in either stack. Open when: deciding whether to stay in a session or start a fresh one, and before leaving one.

His rulings: 10 September 2026, at every turn weigh whether staying or starting fresh is cheaper, and leave a fresh session what it needs; 25 September 2026, the session decides that itself, he never types "checkpoint and stop". Settled with the consultant as decision 0006.

**The shape of the cost.** A session pays a boot once — rulebook, product pages, open pull requests, the slice's code — then works cheaply while the history helps, until it stops helping: stale truth, loops, detail lost to compaction. Too early throws away the boot; too late corrupts the work. Neither is a number a session can read; the signs below it can.

**Stay** only while all three hold: the same slice, or the same bounded advisory question, continues; carrying the history is cheaper than rebuilding the unresolved context from the canonical boot; and the history still helps more than it hurts. Provider caches may inform the second; no cache-age, idle, token, clock or load rule is global. A session resuming mid-slice after a gap verifies the branch, pull request and `main` facts that slice needs before acting, and takes on no rule that landed meanwhile.

**Stop at a boundary**: the slice is merged, parked with its blocker written, or the advisory question settled. The next bounded work starts fresh — always, even in the same repository and files: the slice is the unit, and history carried across a boundary is how stale assumptions cross it unforced. If boots routinely dominate the useful work in planned slices, the slicing is wrong: fix it where the roadmap's `next` lines are written, combining neighbours only where they still form one accepted, user-visible outcome — never by carrying a session over.

**Stop on degradation** inside a slice, on any one of: the repository disproves a material state the session just asserted; the repeated-failure signs `HOW-WE-BUILD.md` owns under *When something goes wrong* — the fresh start it calls for is a session end; the session cannot state the slice, its next action and its open findings without reconstructing them; or the surface explicitly reports the history compacted or summarised. Then no new substantive work: finish the operation in hand, recover enough truth for a coherent checkpoint, write and verify the handover, leave.

**Leaving.** Every durable fact goes into GitHub and the pull request and roadmap handover stand on their own; if the next session's opening words would have to carry project state, it is not finished. Advisory work with no repository yet gets one temporary `START-HERE.md`, superseded once the result is in GitHub. The checkpoint comment on the pull request names its cause — `Checkpoint: boundary — slice complete | parked: <blocker> | advisory settled`, or `Checkpoint: degradation — <sign>` — and the next session's first comment there says whether it held: `Resumed: clean`, or `Resumed: corrected — <what was stale or missing>` (a fact that legitimately changed after the checkpoint is not a correction). Those two lines are the measure: early, a boundary on an unfinished, unblocked slice; on time, a degradation checkpoint resumed clean; late, a correction, above all one no sign preceded.

**And say so, as a claim that can be wrong.** "Ready to start fresh session" states that the repository carries what the next session needs and nothing has to be pasted; a claim gets checked before it is made. On 14 September 2026 a Juku Perfume session ended eight replies that way while `roadmap.json` pointed at deleted code and named no next action; the phrase had become a sign-off. If the Chairman has to type "checkpoint and stop" solely to make a continuing session hand itself over, this mechanism failed.

For Codex, a fresh cloud task starts each slice and a thread continues only inside it while the stay conditions hold.
