# The independent reviewer

Scope: every repository under this rulebook, in either stack. Open when: working out who reviews a change, asking for a read, judging whether a commit is cleared, writing a repository's Review guidelines, checking a product's gate, or changing the review machinery.

**Who.** Step 5 of `HOW-WE-BUILD.md`: one reviewer reads every pull request cold, in every repository. It answers only as the `juku-reviewer` GitHub App's check run. The model behind it is the registry's, by role (`library/model-registry.md`): `reviewer-main` for pages and ordinary code; `reviewer-risky` for a change in one of the six risky classes — pricing logic; live database mutation or schema; authentication and authorisation; public trust-boundary changes; deploy and release machinery; the review gate itself — or with a file whose kind the gate does not know. Every change carries `Personal data or payments affected: yes/no — reason`; hiding, capturing, logging and deleting data all count as yes. The reviewer is not shown the body, so the line binds the builder; the names and what the change is seen to do are the floor, and a "no" never lowers a class. In a product, a change is risky too when a line it adds or deletes sits between `RISK: pricing — START` and `RISK: pricing — END` markers in a code file, each on a line of its own in a comment (Hemz's `PRICING CORE` band counts the same), or when its markers cannot be read; no live read has used a marker yet. Codex does not review. A product never changes who reviews or what a class is owed; that changes here.

**What it reads.** It judges the change, never the design. The diff against `main`'s tip, the tests, and the pages as the change leaves them, as a selection: the touched files (past 40 KB, their touched sections), their partners both ways, the pages naming them and the registry, with every other file named and sized. A reader needing more answers `needs-context` naming a file or one unit of one (no live read has yet been given a function), and is read once more in the same job with it; still short, it signs blocking, "incomplete read". It is never shown the pull request's body or thread, so an answer living only in a comment never reaches it. Its brief is the repository's `AGENTS.md`, read from protected `main`, so a pull request cannot write its own reviewer's instructions. A product read also carries the `roadmap.json` item the pull request's title opens with and the `PRODUCT.md` sections that item names, every other item and section named with its size, and beside the touched files their relative imports, one hop.

**Before asking: the pre-flight.** The repository's own checks run green (all but the gate, red until the read lands), and the builder reads its own diff against the `## Review guidelines` on `main`, its hazards above all, and fixes what it finds. Its effort is measured, never assumed free: the handover records it, unknown where not measured, for the 2 November keep-or-revert test (`library/carries-sessions.md`).

**Asking.** Here, a comment opening `/claude review`; in a product, the ready mark, which the asker reads (`library/product-joins.md`). Ask once per round, after the round's fixes in one push, then stop: the check turns green by itself (that a product's own wake re-runs its gate when a verdict lands is not yet shown on a cited run). Two rounds is the limit. After them a trade-off is the CTO's, with any dissent left on the pull request; a third round means the slice is too big: shrink it. A risky change a read finds that names and markers missed: the builder marks it and asks again within the round limit; found on the last round, the slice parks or shrinks, never a bought extra round, never an ordinary read standing in for a risky one. A claim a test can settle is settled by the test, never by rank; if it cannot be settled safely, the change shrinks or stops. A blocking finding the CTO still disputes goes to the Chairman, never into a third round. An empty answer is asked once more inside the same two reads; a second is never signed as a verdict.

**The verdict.** The read returns findings, each blocking or advisory; the workflow derives the verdict, blocking first. A missing, malformed, unknown-severity or cut-off answer clears nothing. It clears only the commit it read: a later push voids it, and a report to him names that commit. A read with advisory findings alone opens the gate; the CTO takes or leaves them. In this repository the proposer never clears its own addition: a head with a blocking finding stays red until the push that answers it.

**Never a sentence permitting a merge while the check is red**: the one check carries the file lists and the secret scan too, so any such permission waives those with it. Nothing is pasted between models, and nothing passes through the Chairman.

**Why a check run.** Only a GitHub App can create one, and nobody with write access can forge, edit or delete it; a comment can be both. The App's key lives in the environment `reviewer`, which admits `main` alone, and `.github/workflows/door.yml` is the standing proof: a branch named `proof/door-*` must be refused the key. A green door run on a branch means nothing merges until the policy is back.

**What it spends.** One review allowance serves every repository, so asking once per round is the spend guard. Cash is checked before each request against his weekly limit (`library/money.md`); a refused read parks, never falls back. Every verdict ends with a spend line: class, role, exact model, effort, tokens, cost and minutes, totalled over every attempt, cash and plan allowance apart, unresolved attempts counted. GitHub's Actions minutes for private repositories are one small monthly budget he set, stop-at-limit on: spend less rather than raise it (`library/carries-sessions.md`).

**The machine is files.** `review-gate.py` (the register and wiring checks), `.github/workflows/` (the reviewer, the wake, the door, the product reviewer `review-product.yml`, the asker `ask-product-reads.yml`, the canary and monitor, the Roadmap's build), `product-reads/` (the product read's rules, setup script and starter kit) and `check.sh`, which runs them all. A change to the gate is judged by the gate it proposes, so its check prints a `note:` line and the reader weighs the diff, not the green. The App is on all his repositories, by his word of 3 October 2026, not checked from a session. Typing the identity code GitHub emails him is his; generating the key, sealing it into the `reviewer` environment and deleting it from disk are the session's.

**A product's `## Review guidelines`**, at the end of its `AGENTS.md`, the tool being unable to follow a link; the starter kit's copy matches it, and a product fills in only its own hazards and questions:

```
## Review guidelines
Brief: the rulebook's library/reviewer.md. Address the CTO. Form your view from the diff, the tests, PRODUCT.md and roadmap.json before the pull request's account. Look for what is wrong, missing, duplicated, untested or wider than the slice, and never manufacture disagreement; say what you checked, what you did not, and how sure you are; mark each finding blocking or advisory. A read clears only the commit it read. Two rounds at most; a product question goes to him as "Decision needed: …". Plain English; never write a file. Hazards here: <the product's own>.
Exam, on a change to AGENTS.md, CLAUDE.md, NAMES.md, design/ or design-system.md: answer each question it affects from the pages as they will stand, naming the owning page; a wrong owner, two pages disagreeing, or none answering is blocking. <2–5 questions: which page owns this product's look, money, words, and its approved exceptions>.
```
