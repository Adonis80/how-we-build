# AGENTS.md — how-we-build

What is particular here: this repository is the rulebook, not a product. It changes only by pull request against protected `main`. Adding a rule, step, file, check or agent needs the charter's gate (§13) or the Chairman's own ruling; removing one, or correcting wording, needs neither. The proposer does not clear its own addition: `check.sh` is green only on a commit a reviewer has read and left nothing blocking on, and the answer to a blocking finding is a push the reviewer reads afresh. A disputed blocking finding goes to the Chairman. An advisory finding opens the gate and stays standing, the CTO's to take or leave; which a finding is, the reviewer says. There is no `roadmap.json`: the queue is the open pull requests (`library/changing-the-rulebook.md`).

**One reviewer**, answering only as the `juku-reviewer` App's check run (`library/reviewer.md`), its model routed by risk from `model-registry/registry.json`. **A gate change is judged by the gate it proposes**: a change to `check.sh`, `review-gate.py`, `product-reads/` (`rules-check.py` included) or a workflow clears on the same single read, by `reviewer-risky`, which is then the lead's own model reading the gate; `check.yml` runs the head's own `check.sh`, and a `note:` line says so; weigh the diff, not the green.

## Review guidelines
Brief: `library/reviewer.md`. Address the CTO. Form your view from the diff and the existing pages before the pull request's own account. With each finding say what you checked, what you did not, and how sure you are. Mark each finding blocking or advisory, or needs-context naming the files the read lacked, which is read once more with them; give every finding in one read. Two rounds at most. Prefer a deletion to another exception; do not manufacture disagreement; never write a file into this repository. For each rule a change touches, its owner and the pages that lean on it stay consistent: block a demonstrated contradiction, a retained superseded instruction, or a deletion or move that loses a live requirement, naming the counterexample; extra length alone is never blocking. Hazards particular here: an addition to how we build without the gate or the Chairman's ruling; a file not on the list; provider-specific detail leaking into a global rule; a rule kept in prose that `check.sh` could hold; any claim that *build* is self-sufficient when a fresh session in either stack could not actually recover the work; **a gate change, which is one read of the gate by the gate it proposes**, so weigh such a change on the diff and treat a clean pass on it as the weakest evidence in this repository rather than the strongest; a gate change whose `note:` line is missing, or waved through on the strength of a green the change itself produced; the gate's register of reviewers and the wake job's condition drifting apart, so a read lands that nothing re-runs the check for; the reviewer workflow gaining any trigger beyond `issue_comment`, or losing its `environment: reviewer` line, either of which lets a branch run a reviewer of its own writing or reach the key it signs with; its ask reachable by somebody who cannot already write here, this repository being public and its reviewer spending a shared allowance; the Roadmap's build, `build-board.yml`, printing anything a product holds or a key into this repository's public logs, gaining a trigger, a wider token, an App key or a read, checking out anything of a pull request, uploading an artifact, or able to leave a deploy live that no smoke has passed; the Roadmap's function, `board/build.py`, reading with more than a GET, from a host beyond GitHub and OpenRouter's daily activity, following a redirect, sending one key to the other's host, or reading a product off the map; the product reviewer, `review-product.yml`, printing anything a product holds into this repository's public logs, signing a commit it was not given, reading a product the README's map does not list, or holding a token that reaches past the one product; the asker, `ask-product-reads.yml`, gaining any trigger beyond `workflow_dispatch` and its one ten-minute `schedule` (his ruling, 4 October 2026: the only timer under this rulebook, no product gets one), asking twice about a commit, retrying a read that failed, reading a GitHub error as "nothing ready", holding a token past read on one product, or asking for a read `review-product.yml` would refuse; `product-reads/` changed without its selftests, or the starter kit's gate or wake drifting from the rulebook's own; and machinery described on a page before a run has shown it working, which is the failure [#34](https://github.com/Adonis80/how-we-build/pull/34) closed on and [#38](https://github.com/Adonis80/how-we-build/pull/38) repeated.

## The exam
On a change to `HOW-WE-BUILD.md`, `README.md`, `CHARTER.md` or a library page, answer each question below that the change could affect, from the pages as the change leaves them. Each answer names its owning page. A wrong owner, two pages giving different answers, or no page answering is blocking. A question is added or removed with its rule; the brief is read from `main`, so a change is judged by the questions already there (decision 0021).

1. On a Hemz screen, does HyperSolid or Hemz's own pages decide the look? — HyperSolid (`HOW-WE-BUILD.md`, *Which rule wins*); Hemz supplies tokens, units, money and domain law, and dated picture approvals.
2. A product's constitution says "no spatial layer" with no dated picture approval. Does it bind? — No; void (*Which rule wins*).
3. Memory says one thing, the rulebook another. Which wins? — The rulebook; memory is never a rule.
4. `PRODUCT.md` and `roadmap.json` disagree. Which wins? — `PRODUCT.md`; the copy is corrected (*Which rule wins*).
5. Who decides a product's prices, figures and how it looks? — The Chairman (*Who decides*).
6. Who decides a technical question, and may the session ask him? — The CTO; never ask him.
7. Who merges a green pull request? — The session itself (loop step 7; `library/changing-the-rulebook.md` here).
8. How many review rounds, and what after them? — Two; then the CTO's call, dissent left standing; a disputed blocking finding goes to him (`library/reviewer.md`).
9. The reviewer is unreachable. What happens? — The slice parks, one comment, the next item begins (`library/reviewer-parking.md`).
10. May a session set a timer to check back later? — No (`HOW-WE-BUILD.md`, the loop).
11. Where does a new rulebook rule's text go, and what must leave? — Its one home; what it supersedes, in the same pull request (`library/changing-the-rulebook.md`).
12. A change needs more words than the budget allows. What then? — Cut elsewhere in the same pull request; never a declared exception.
13. What must a product's constitution contain, and nothing else? — Tokens, Units, Money, Domain law, Approved by picture (dated, with the picture).
14. Where are past decisions, and when are they read? — The archive; only when asked why (`README.md`).
15. What reaches the Chairman, and how? — Money, permissions, product truth or a picture, self-contained (*Asking the Chairman*).
16. What ends every reply to him? — "continue to build here" or "ready to start fresh session" with where and what to type.
17. What does "build" mean? — Take the top ready item; never a question (`HOW-WE-BUILD.md`).
18. Where do a product's words change, and where does code? — Words from Cowork through the Mac by pull request; code in a code session attached to the repository (`library/two-stacks.md`).
19. Which file names a model? — `model-registry/registry.json` alone.
20. A visual design is drawn with words and figures inside the picture. Allowed? — No; they go in by machine (`library/hypersolid.md`, step 3).
