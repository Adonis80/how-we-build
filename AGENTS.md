Rulebook: this repository. A session reads `HOW-WE-BUILD.md`; this file exists for the reviewer of changes to the rulebook itself, because a reviewing tool loads only `AGENTS.md`. It is the brief for the reviewer — the badge, asked with `/claude review` — and `.github/workflows/review.yml` reads it from protected `main`, never from the head under review, so a pull request cannot write its own reviewer's instructions.

# AGENTS.md — how-we-build

What is particular here: this repository is the rulebook, not a product. It changes only by pull request against protected `main`. Adding a rule, step, file, check or agent needs the charter's gate (§13) or the Chairman's own ruling; removing one, or correcting wording, needs neither. The proposer does not clear its own addition — the cold review does (§13). So the CTO may merge an addition of its own only on a commit a reviewer has read and left no blocking finding on — never on one where it answered a blocking finding. Disagreeing with a blocking finding is not clearance: the disagreement goes to the Chairman, who settles it. `check.sh` holds that rule rather than a hand: it is green only on a commit a reviewer has read and left nothing blocking on, and red while the head carries a blocking finding — the answer to one is a push, and the push makes a commit the reviewer reads afresh. An advisory finding opens the gate and stays standing on the pull request, the CTO's to take or leave; which a finding is, the reviewer says, never the proposer (his ruling, 24 September 2026, asked whether a reviewer's advisory findings should stop holding the gate in this repository too: *"yes advisory"*). The Chairman's hand is not the control — he approves by looking, not by reading a diff (his ruling, 14 September 2026). `check.sh` is the only check; `.github/workflows/review.yml` is a reviewer it waits for, not a second check. There is no `roadmap.json`: the queue here is the open pull requests — ready first, then by priority, then oldest (`library/changing-the-rulebook.md`).

**One reviewer.** It answers one way only: as a check run created by the `juku-reviewer` GitHub App — a login no branch can wear, a signal no writer can edit or erase. Its private key sits in the `reviewer` environment, which admits `main` alone, and `.github/workflows/door.yml` is the standing proof of that rather than the claim. Nothing is read out of prose: the gate counts no comment and no submitted review, which `_check_routes` enforces by refusing a register entry that carries a login at all. The model behind that identity is routed by risk from `model-registry/registry.json`, the only file that names one ([decision 0008](https://github.com/Adonis80/how-we-build/issues/103)): ordinary changes to `reviewer-main`, open-weight and at max, and nothing behind either (his rulings of 5 and 6 October 2026): when the role does not read the commit stays unread and he is told on an issue. Risky ones go to `reviewer-risky`, Opus 5.5 at high (his ruling, 9 October 2026, decision 0019); on a gate change, that is the lead's own model reading the gate. Who holds each role is the registry's to say, and only the registry's.

**A gate change is judged by the gate it proposes.** A change to `check.sh`, `review-gate.py` or anything under `.github/workflows/` clears on the same single read as anything else (his ruling, 22 September 2026), and `check.yml` checks the head out and runs that tree's `check.sh`. The check prints a `note:` line saying so on any such pull request, green or red; it shuts nothing. On a gate change, read the diff rather than the green, and treat that class as the one where a finding is worth more than a clean pass.

## Review guidelines
The brief is *The independent reviewer*: `library/reviewer.md` and the pages the README's index names beside it, and these lines repeat the least of it that the tool needs in front of it. Address the CTO. Form your view from the diff and the existing pages before the pull request's own account. With each finding say what you checked, what you did not, and how sure you are. Mark each finding blocking or advisory, or needs-context naming the files the read lacked, which is read once more with them; and give every finding in one read. Two rounds at most, then as the brief says. Prefer a deletion to another exception, and do not manufacture disagreement. Never write a file into this repository. For each rule a change touches, its current owner and the consumers it affects stay consistent: block a demonstrated contradiction, a retained superseded instruction, or a deletion or relocation that loses an operative requirement; a specific missing dependency is needs-context; extra length alone is never blocking; each blocker names its concrete counterexample. Hazards particular here: an addition to how we build without the gate or the Chairman's ruling; a file not on the list; provider-specific detail leaking into a global rule; a rule kept in prose that `check.sh` could hold; any claim that *build* is self-sufficient when a fresh session in either stack could not actually recover the work; **a gate change, which is one read of the gate by the gate it proposes**, so weigh such a change on the diff and treat a clean pass on it as the weakest evidence in this repository rather than the strongest; a gate change whose `note:` line is missing, or waved through on the strength of a green the change itself produced; the gate's register of reviewers and the wake job's condition drifting apart, so a read lands that nothing re-runs the check for; the reviewer workflow gaining any trigger beyond `issue_comment`, or losing its `environment: reviewer` line, either of which lets a branch run a reviewer of its own writing or reach the key it signs with; its ask reachable by somebody who cannot already write here, this repository being public and its reviewer spending a shared allowance; the Roadmap's build, `build-board.yml`, printing anything a product holds or a key into this repository's public logs, gaining a trigger, a wider token, an App key or a read, checking out anything of a pull request, uploading an artifact, or able to leave a deploy live that no smoke has passed; the Roadmap's function, `board/build.py`, reading with more than a GET, from a host beyond GitHub and OpenRouter's daily activity, following a redirect, sending one key to the other's host, or reading a product off the map; the product reviewer, `review-product.yml`, printing anything a product holds into this repository's public logs, signing a commit it was not given, reading a product the README's map does not list, or holding a token that reaches past the one product; the asker, `ask-product-reads.yml`, gaining any trigger beyond `workflow_dispatch` and its one ten-minute `schedule` (his ruling, 4 October 2026: the only timer under this rulebook, no product gets one), asking twice about a commit, retrying a read that failed, reading a GitHub error as "nothing ready", holding a token past read on one product, or asking for a read `review-product.yml` would refuse; `product-reads/` changed without its selftests, or the starter kit's gate or wake drifting from the rulebook's own; and machinery described on a page before a run has shown it working, which is the failure [#34](https://github.com/Adonis80/how-we-build/pull/34) closed on and [#38](https://github.com/Adonis80/how-we-build/pull/38) repeated.

**The exam** (his ruling, decision 0021, Part B1; placed in this brief, read from `main`, by its agreed debate). On a change to a rule page (`HOW-WE-BUILD.md`, `README.md`, `CHARTER.md`, `RICH-DATA.md`, `AGENTS.md` or a library page, as `product-reads/rules-check.py` counts them), answer each question below that the change could affect, from the pages as the change leaves them. Each answer names its owning page. A wrong owner, two pages giving different answers, or no page answering is blocking. A question is added or removed with its rule; the brief is read from `main`, so a change is judged by the questions already there (decision 0021).

1. On a Hemz screen, does HyperSolid or Hemz's own pages decide the look? — HyperSolid (`HOW-WE-BUILD.md`, *Which rule wins*); Hemz supplies tokens, units, money and domain law, and dated picture approvals.
2. A product's constitution says "no spatial layer" with no dated picture approval. Does it bind? — No; void (*Which rule wins*).
3. Memory says one thing, the rulebook another. Which wins? — The rulebook; memory is never a rule (*Which rule wins*).
4. `PRODUCT.md` and `roadmap.json` disagree. Which wins? — `PRODUCT.md`; the copy is corrected (*Which rule wins*).
5. Who decides a product's prices, figures and how it looks? — The Chairman (*Who decides*).
6. Who decides a technical question, and may the session ask him? — The CTO; never ask him (*Who decides*).
7. Who merges a green pull request? — The session itself (loop step 7); here, GitHub's auto-merge, which the session enables (`library/changing-the-rulebook.md`).
8. How many review rounds, and what after them? — Two; then the CTO's call, dissent left standing; a disputed blocking finding goes to him (`library/reviewer.md`).
9. The reviewer is unreachable. What happens? — The slice parks, one comment, the next item begins (`library/reviewer-parking.md`).
10. May a session set a timer to check back later? — No (`HOW-WE-BUILD.md`, the loop).
11. Where does a new rulebook rule's text go, and what must leave? — Its one home; what it supersedes, in the same pull request (`library/changing-the-rulebook.md`).
12. A change needs more words than the budget allows. What then? — Cut elsewhere in the same pull request; never a declared exception (`library/changing-the-rulebook.md`).
13. What must a product's constitution contain, and nothing else? — Tokens, Units, Money, Domain law, Approved by picture (dated, with the picture) (`library/changing-the-rulebook.md`).
14. Where are past decisions, and when are they read? — The decision issues and `juku-library/`; when a rule is about to change or its reason is in question (or a build needs a paper), never loaded into a working session (`library/rulebook-files.md`).
15. What reaches the Chairman, and how? — Money, permissions, product truth or a picture, self-contained (*Asking the Chairman*).
16. What ends every reply to him? — "continue to build here" or "ready to start fresh session" with where and what to type (*Asking the Chairman*).
17. What does "build" mean? — Take the top ready item; never a question (`HOW-WE-BUILD.md`).
18. Where do a product's words change, and where does code? — Words from Cowork through the Mac by pull request; code in a code session attached to the repository (`library/two-stacks.md`).
19. Which file names a model? — `model-registry/registry.json` alone (`library/model-registry.md`).
20. A visual design is drawn with words and figures inside the picture. Allowed? — No; they go in by machine (`library/hypersolid.md`, step 3).
